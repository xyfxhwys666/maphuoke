# MapSearch 地图获客平台项目总结与面试讲解文档

> 本文面向第一次接触项目的读者，也面向面试时需要完整介绍项目的开发者。内容以仓库中的实际实现为依据，重点解释系统为什么这样设计、代码分别负责什么、一次任务如何从输入走到结果，以及项目中可以展开的工程难点。

## 1. 先用一句话理解项目

MapSearch 是一个面向企业获客的地图线索采集平台。用户输入“在某些城市寻找某类企业，并且需要手机、邮箱或微信”等自然语言需求，系统自动把需求解析成结构化采集计划，按城市和关键词调用地图搜索能力发现候选企业，再用地图详情确认企业名称、地址和联系方式，必要时通过公开网页和大模型补充企业信息，最后执行证据校验、去重合并和 ERP 投递。

它解决的不是单次搜索问题，而是把人工重复执行的“搜关键词、看地图、判断是不是目标企业、找联系方式、复制到业务系统”变成一个可追踪、可暂停、可恢复、可重试、可交付的任务系统。

面试中可以这样开场：

> 我参与的是一个地图获客和线索交付平台。系统接收自然语言采集需求，将其解析为城市乘关键词的工作单元，先通过公开网页或地图关键词搜索发现真实公司名称，再用地图精确查询获取 POI 详情和联系方式，之后完成相关性判断、字段级证据校验、去重合并和 ERP 幂等投递。后端使用 FastAPI、Pydantic、SQLAlchemy 和 Playwright，前端使用 React、TypeScript 和 Vite，系统重点解决了外部网页不稳定、登录和安全验证、长任务状态恢复、重复数据和重复投递等问题。

这段话已经覆盖了业务目标、核心链路、技术栈和工程难点。后面的内容用于把每一个词讲清楚。

## 2. 技术栈总览

项目采用前后端分离架构，后端以 Python Web 服务和领域建模为核心，前端以 React 工作台为核心，浏览器自动化和外部 Provider 负责连接地图、模型与 ERP。下面的技术栈不仅用于“列技能”，每项技术都对应项目中的实际职责。

## 3. 业务背景和要解决的问题

### 2.1 原来的人工流程

传统获客流程通常是这样的：运营人员先确定城市和行业，然后在地图中输入关键词；地图返回的结果可能是公司、门店、园区、楼宇、个人商户或者与行业无关的地点。人工需要逐条判断名称是否真实、是否属于目标业务，再打开详情页查看电话和地址。很多地图结果只有座机或者没有联系方式，人工还要继续搜索企业官网、公众号、招聘页或其他公开页面，寻找手机、邮箱和联系人。最终符合条件的数据还要复制到 CRM 或 ERP 系统。

这个过程有几个明显问题。第一，人工操作慢，城市越多、关键词越多，重复劳动越严重。第二，搜索结果不是结构化企业数据，名称可能被截断、简称可能不一致，同一家公司会在多个关键词下重复出现。第三，地图页面依赖浏览器登录状态、页面加载速度和安全验证，自动化程序不能简单地把它当作一个永远稳定的 HTTP 接口。第四，联系方式具有业务风险，模型猜出来的号码不能直接当作真实号码，更不能无条件投递到下游系统。第五，任务可能运行几十分钟甚至更久，进程重启或浏览器暂时不可用时，系统应该能继续，而不是从头开始。

### 2.2 项目的业务目标

项目把上述过程抽象成四个目标：

1. 让用户用自然语言描述需求，减少填写大量技术参数的成本。
2. 将模糊需求转成可执行的城市、关键词、模型和联系方式条件。
3. 通过多来源采集和证据模型，提高结果的真实性与可解释性。
4. 把长任务变成有状态的工作流，支持暂停、恢复、取消、失败重试和结果幂等交付。

### 2.3 项目边界

项目不是一个通用搜索引擎，也不是让大模型凭空生成企业名单。地图或公开网页负责提供可观察的来源信息，大模型主要用于关键词扩展、候选相关性判断和公开信息整理。最终能否作为有效线索，要看企业名称是否精确匹配、联系方式是否满足要求、字段是否有来源证据，以及是否满足投递策略。

这一点在面试中很重要。可以主动说明：模型是辅助决策组件，不能替代来源系统；地图详情中的真实号码优先级高于模型猜测；没有证据的字段可以展示，但默认不能作为自动投递依据。

## 4. 总体架构

项目采用前后端分离结构，代码位于 `.worktrees/map-lead-platform`。前端负责任务创建、进度展示、控制操作和结果交付；后端负责业务编排、外部 Provider 调用、状态机、持久化和批处理。

```text
React + TypeScript + Vite
        |
        | JSON HTTP API
        v
FastAPI 路由层
        |
        +-- collection service：自然语言采集任务
        +-- company search service：单公司搜索任务
        +-- batch job manager：CSV/XLSX 批量任务
        +-- connector facade：外部系统稳定接口
        |
        +-- intent / planner：意图解析与工作单元规划
        +-- domain：标准化、去重、合并、证据、状态
        +-- providers：地图、浏览器、公开网页、模型、ERP
        |
        v
SQLAlchemy Repository -> SQLite 默认数据库
```

### 4.1 后端分层

`backend/app/api` 是 HTTP 入口。路由负责校验请求、查找任务、调用服务并把领域对象转换为返回 JSON，不把复杂的采集逻辑塞进路由函数。

`backend/app/collection` 是自然语言采集主领域。`intent.py` 解析城市、关键词、模型、联系方式和数量；`planner.py` 根据解析结果建立城市乘关键词矩阵；`service.py` 执行工作单元、维护状态、合并结果、计算摘要和处理交付。

`backend/app/services` 放通用服务。`search_task.py` 面向单个公司搜索，`enrichment.py` 负责信息补全，`verification.py` 负责证据验证，`delivery.py` 负责投递，`batch_jobs.py` 管理文件导入后的批量执行。

`backend/app/domain` 是与具体 Provider 无关的核心模型和规则。这里可以看到 `MapPoiCandidate`、`LeadRecord`、`EvidenceValue` 等模型，也包含手机号、电话、邮箱、微信和公司名称标准化，身份去重，字段合并，投递门禁和状态转移。

`backend/app/providers` 是外部依赖适配层。地图既支持 Web Provider，也支持 API Provider；大模型通过 Doubao Web Gateway 或其他模型适配器提供能力；公开网页 Provider 负责发现公司名称和验证联系方式；ERP Adapter 负责构造下游 payload 并发送请求。Provider 通过 Protocol 或抽象接口接入，核心服务不需要知道浏览器页面选择器的细节。

`backend/app/storage` 是持久化层。Repository 把 Pydantic 领域对象保存到 SQLAlchemy ORM 表中，并在读取时恢复为领域模型。这样服务层不需要到处拼 SQL，也方便使用 Fake Provider 做测试。

### 4.2 前端分层

`frontend/src/App.tsx` 是页面入口，负责在不同工作台之间切换，并提供旧版单公司任务、批量任务和新版自然语言采集工作台。

`CollectionWorkbench.tsx` 是新版主界面。它维护自然语言请求、模型选项、连续采集开关、自动投递开关、任务列表、当前任务、工作单元进度、结果表格和 ERP 交付状态。前端不自己判断业务有效性，而是把后端返回的状态、统计数字和证据字段转成可读展示。

`api.ts` 集中封装 HTTP 请求。每个函数对应一个后端 API，例如创建采集任务、开始、暂停、恢复、取消、重试、单条投递和批量投递。`types.ts` 定义前后端共享语义的 TypeScript 类型，保证任务状态、工作单元状态、证据字段和交付结果在前端有明确结构。

## 5. 用户请求如何变成采集计划

这是项目最适合面试展开的链路之一。用户可能输入：

> 在深圳和广州找做住宅全屋定制的公司，需要手机，尽量找 100 个有效线索，可以用豆包判断相关性。

系统不会把整句话直接拼到地图搜索框里，而是分成意图解析和计划生成两步。

### 5.1 意图解析

`collection/intent.py` 中的 `parse_collection_intent` 是入口。它接收原始文本、已配置模型集合以及可选的模型关键词建议，输出 `ParsedCollectionIntent`。

解析结果包含：

- `cities`：明确提到的城市列表。
- `all_cities`：没有指定城市时是否使用系统配置的三线及以上城市集合。
- `city_scope_label`：用于页面展示的城市范围描述。
- `keywords`：原始行业词和扩展后的搜索词。
- `models`：相关性判断使用的模型。
- `required_contacts`：需要手机、邮箱、微信中的哪些字段。
- `contact_match`：多个联系方式要求是任意一个满足，还是全部满足。
- `limit_per_city`：每个城市的数量限制。
- `target_valid_contacts`：整个任务希望得到的有效联系方式数量。
- `competitor_terms`：住宅、家具等场景下用于排除明显无关公司的竞争词。

城市提取会遍历配置的城市名称，同时处理带“市”和不带“市”的写法；关键词提取先匹配常见业务词，如果没有匹配到，再从“寻找某某公司”“做某某业务的企业”等目标句式中提取带行业后缀的短语；如果仍然没有结果，会使用默认行业关键词。

联系方式提取使用词组映射。例如“手机、手机号、电话”归到 `mobile`，“邮箱、email”归到 `email`，“微信、微信号”归到 `wechat`。如果用户没有明确说，系统默认要求手机。多个字段的匹配策略根据“全部需要”“同时具备”等词判断为 `all`，否则通常是 `any`。

数量解析会限制在合理范围内，避免用户输入极大数字导致一次创建过多工作。对“越多越好”“尽可能多”等语义，项目有默认有效手机号目标，防止连续模式没有停止条件。

### 5.2 关键词扩展

住宅类需求不是一个固定关键词。用户说“全屋定制”，真实企业名称可能包含“住宅装修”“别墅装修”“室内设计”“整装公司”等不同词。项目在检测到住宅范围后，会从一组经过验证的关键词矩阵开始，再合并模型给出的额外变体，并过滤明显无关的关键词，例如招聘、培训、供应商、材料、品牌或产品等词。

对深圳这类高数据量城市，如果用户表达“多找一些”或“100 个”，系统还会将深圳各区和多个行业后缀组合成额外关键词，例如“某区全屋定制公司”“某区装修设计公司”。扩展结果会去重并设置上限，避免自然语言扩展无限膨胀。

这里体现了一个工程取舍：意图解析不是完全交给大模型。城市、数量和联系方式这些字段使用确定性规则，结果更可控；模型可以提供关键词建议，但不能绕过业务过滤。测试中也验证了明确关键词、默认关键词、住宅扩展、噪声过滤和目标数量优先级。

### 5.3 工作单元规划

`collection/planner.py` 中的 `build_work_units` 将城市和关键词做笛卡尔积。假设有 2 个城市和 10 个关键词，就会产生最多 20 个工作单元。每个单元包含城市、关键词、Provider、模型、联系方式要求、匹配策略和每城限制。

每个工作单元 ID 不是随机临时值，而是将任务种子、城市、关键词和 Provider 拼接后做 SHA-256，截取固定长度生成稳定 ID。这样任务恢复、重复计划生成和持久化读取时都能保持身份稳定，也便于判断同一个城市和关键词是否已经执行过。

工作单元是长任务可恢复的关键。系统不是把所有城市和关键词放在一个大循环中只保存一个总进度，而是把每个可重试边界单独记录。某个城市关键词失败时，其他已成功单元不会被重做；如果用户暂停，系统可以从当前单元或下一个未完成单元继续。

## 6. 自然语言采集的完整执行链路

### 5.1 创建任务只做规划

HTTP 请求进入 `POST /api/v1/collection-tasks/from-natural-language`。路由校验请求字段，调用 Collection Service 创建任务。创建阶段解析意图、生成工作单元并保存任务，但不会立刻触发地图搜索。这样用户可以先检查城市范围、关键词数量、模型配置和预估工作量，再点击开始。

这也是前后端职责清晰的体现：创建接口是一个纯规划动作，开始接口才触发外部副作用。测试中明确验证了“创建任务不会搜索”，避免用户误点击或浏览页面时就启动浏览器采集。

### 5.2 开始任务

调用 `POST /api/v1/collection-tasks/{task_id}/start` 后，Collection Service 将任务置为运行状态，启动异步执行或后台线程，并按顺序选择待执行工作单元。任务的 `checkpoint` 会记录当前阶段、当前工作单元 ID、浏览器状态、已完成单元、失败单元和重试时间。

执行过程中，每个单元通常经历以下步骤：

```text
工作单元开始
  -> 发现真实公司名称
  -> 对公司名称做排除和去重
  -> 地图精确查询公司名称 + 城市
  -> 验证 POI 是否真的是该公司、该城市
  -> 模型判断是否属于目标业务
  -> 合并地图字段与补充字段
  -> 公开证据校验联系方式
  -> 计算有效线索和城市限制
  -> 可选地投递 ERP
  -> 保存单元状态和任务摘要
```

### 5.3 公司名称发现

直接把“全屋定制公司”作为地图查询词，可能返回大量泛化 POI，也可能没有公司全称。项目增加了公司名称发现阶段：通过公开搜索页或地图关键词结果提取真实出现的公司名称、城市、命中关键词、来源 URL 和证据引用，形成 `CompanyNameCandidate`。

公开网页 Provider 使用标准库 HTMLParser 解析可见结果，清理标题前后缀，过滤搜索导航页和明显不是公司名称的内容。地图关键词发现作为补充来源。当公开搜索没有结果时，系统仍然可以使用地图关键词返回的名称继续执行，但会保留 `discovery_channel`，让后续知道名称来自哪里。

系统还会判断同一个公司是否已经在其他任务或更早的工作单元中搜索过，避免重复调用地图。跨来源发现的同名企业会合并来源 URL 和引用，而不是创建多条相同线索。

### 5.4 地图精确查询

地图部分有两类 Provider：`AmapWebProvider` 和 `AmapApiProvider`。Web Provider 通过专用 Chrome 的 CDP 连接，在真实页面中输入查询、等待结果、打开详情页并读取可见文本；API Provider 在配置 Key 时调用地图 API，并将 POI 转成统一的 `MapPoiCandidate`。

两类 Provider 都实现统一的地图发现协议，Collection Service 只依赖 `search_company` 或 `search_keyword`，不直接操作 Playwright 页面，也不关心 API 响应的具体字段。

“公司名称 + 城市”的精确查询非常关键。宽泛关键词结果只用于发现候选名称，不能直接当成最终企业。精确查询后，系统会检查返回 POI 的名称是否与候选公司名称匹配、所在城市是否与任务城市一致，并拒绝楼宇、园区、商圈或只有模糊相似度的结果。这样可以降低把错误 POI 当作目标公司的风险。

地图候选 `MapPoiCandidate` 保存公司名、城市、地址、座机、手机、类别、经纬度、POI ID、详情 URL、来源 URL、原始文本、来源元数据、采集时间和证据快照 ID。对于地图详情文本，项目会优先识别手机字段；座机放在 `telephone`，不会错误地把 400 或固定电话当成手机。

### 5.5 浏览器生命周期与人工介入

地图 Web Provider 依赖真实浏览器，所以项目没有让业务代码直接创建很多散落的 Page，而是用 `browser/lifecycle.py` 和 `browser/actor.py` 封装浏览器生命周期和串行操作。

Dedicated Browser 负责启动或连接带独立 profile 的 Chrome、连接 CDP、创建上下文、导航、重新连接和关闭。Browser Actor 用单独的工作线程或命令队列串行执行浏览器操作，对超时操作替换 worker，避免一个卡死的页面阻塞后续所有任务。

浏览器状态不仅有 running 和 stopped，还会检测登录、挑战、端口占用、浏览器断开等情况。当检测到登录页或安全验证时，Provider 抛出带状态信息的 ProviderPaused，服务层把任务变成 `needs_attention` 或等待状态，并保存浏览器状态。用户在 Chrome 中完成登录或安全验证后，再点击恢复，任务可以继续。

这比无限重试更安全。登录和滑块验证不是网络异常，自动重试只会增加失败次数；把它显式建模为“需要人工处理”，用户才能知道下一步做什么。

### 5.6 相关性判断

候选地图结果不一定属于目标行业。项目通过 `RelevanceJudge` 协议接入 Doubao 或其他模型。模型输入包含公司名称、城市、类别、地址、来源文本和业务关键词，输出结构化的 `relevant`、`not_relevant` 或 `review`，并附带原因、置信度和模型 ID。

模型响应不能直接信任。`doubao_parser.py` 会尝试提取 JSON，检查状态值是否有效、公司名称是否与请求公司匹配、字段类型是否正确，并清理模型可能返回的“未知”“无法确认”“猜测”等值。解析失败会成为可重试错误，而不是静默生成一个 LeadRecord。

多个模型的结果保存在 `relevance_decisions` 中。系统可以合并相同候选的多个判断，并据此决定相关、无关或需要人工复核。这样可以保留决策轨迹，面试中可以解释为“模型输出是可审计决策，不是覆盖式的布尔字段”。

### 5.7 信息补全

相关企业进入补全阶段时，`DoubaoEnrichmentService` 调用统一的 `DoubaoEnrichmentGateway`。Gateway 负责打开模型页面、提交提示词、等待可见结果和解析响应；服务层负责将补全结果合并到 LeadRecord。

提示词会明确要求结构化字段，例如公司全称、手机、座机、联系人、联系人职务、邮箱、微信、地址、业务介绍、来源链接和证据引用。同时要求模型区分“页面真实出现”和“无法确认”，不要用推测值填充。

合并策略不是模型返回什么就覆盖什么。地图详情中的公司名称、城市、地址和手机属于高优先级字段；模型补充的联系人、邮箱、微信和服务介绍可以补充空值；已有的可信手机不能被模型的座机或猜测值替换。`domain/merge.py` 把字段合并规则集中起来，避免每个业务流程用不同的优先级。

### 5.8 证据校验

项目的核心质量思想是“字段和证据绑定”。`EvidenceValue` 记录值、状态、来源 URL 和引用内容，状态从 `captured` 到 `source_backed` 再到 `verified`。

地图采集到的信息通常先是 `captured`，表示确实从页面或 API 抓到了；公开网页验证到公司或联系方式时，可以提升到 `source_backed`；通过明确的独立证据、手机号在地图详情中出现并与公司匹配等条件后，才允许标记 `verified`。

联系方式验证由地图证据验证器和公开网页证据验证器共同参与。公开网页验证器可以访问候选来源、提取可见文本、检查联系方式是否出现，并保留包含号码或邮箱的短引用。它不会仅凭搜索标题就断言联系方式属于公司。

### 5.9 有效线索、城市限制和任务完成

有效线索数量不是简单的 `len(results)`。系统要先检查手机号是否是合法移动号码，来源是否可信，企业是否没有被判定为无关，并按照公司和手机号身份去重。

每个城市可以有 `limit_per_city`，但限制计算的是唯一有效手机，而不是搜索结果条数。同一家公司在不同关键词下出现多次，只计一次；同一手机对应同一公司，也不能重复计数。达到城市上限后，后续关键词工作单元会标记为 `skipped_limit`。

任务整体有三种主要结束原因：达到目标有效联系方式数量时是 `target_reached`；所有来源和工作单元都执行完但没有继续结果时是 `source_exhausted`；有无法恢复的工作单元失败时是 `completed_with_errors`。连续模式可以在每日进度和目标约束下继续运行，扩展关键词时只追加新工作单元，不重放旧单元。

## 7. 单公司任务、批量任务与自然语言任务

项目中同时保留了三种使用方式，它们共享领域模型和 Provider，但入口不同。

### 6.1 单公司任务

旧版单公司 API 通过 `company-search-tasks` 创建任务，输入公司名称、城市、需要的联系方式、地图 Provider 和补全 Provider。它适合用户已经知道企业全称的场景，流程更直接：地图搜索公司、补全信息、验证、投递。

`services/search_task.py` 维护单公司级别的 `CompanyProgress`，记录发现、补全、验证、交付状态、重试次数、下次重试时间和最后错误；`TaskCheckpoint` 记录当前公司、已完成公司、失败公司、浏览器状态、操作 ID 和交付指纹。

### 6.2 批量任务

批量入口支持 CSV 和 XLSX。`batch/importers.py` 负责读取文件、识别公司名称和城市列、规范化列名、按行报告错误，并在导入阶段按公司身份去重。缺少必需列时会返回明确的行号和字段错误，而不是等到执行阶段才失败。

`BatchJobManager` 把每一行变成 BatchItem，保存队列状态、关联的单公司任务 ID、候选数量、错误和重试次数。批量执行按项目逐条处理，某一条失败不会丢失其他成功项。用户可以暂停整个批量任务、恢复、只重试错误项，最终状态可以是全部完成或部分失败。

### 6.3 自然语言采集任务

自然语言采集是当前业务功能最完整的入口。它先做城市乘关键词规划，再执行大量工作单元，适合从“行业范围”发现企业，而不是处理一张已知公司表。它还包含公司名候选、相关性判断、持续采集、目标手机号统计、来源耗尽判断和批量 ERP 投递。

三种任务并不是三套完全独立的代码。它们共享 `MapPoiCandidate`、`LeadRecord`、标准化、证据、投递和存储机制，降低了实现重复和行为不一致的风险。

## 8. 数据模型怎么设计

### 7.1 Candidate 和 Lead 的区别

`MapPoiCandidate` 是“地图发现结果”，它描述地图或搜索来源里看到的一个候选 POI。它可能只有公司名和地址，也可能有手机；此时还不能保证它满足最终业务条件。

`LeadRecord` 是“经过处理的业务线索”。它会包含补全字段、证据字段、验证状态、模型来源、交付状态和指纹。一个 Lead 可以由地图候选和模型补全合并得到，也可以在多次关键词查询中被更新。

拆分这两个模型有三个好处：可以保留原始采集事实；可以重跑补全和验证而不重复地图查询；可以让前端展示“发现了什么”和“最终可交付什么”两个层次。

### 7.2 证据字段

每个关键字段可以有自己的 `EvidenceValue`，而不是只在 Lead 顶层放一个总状态。例如手机可能是地图详情捕获，邮箱可能是公开网页支持，联系人姓名可能仍然没有证据。交付门禁根据请求字段逐个判断，而不是因为公司名称有来源就把所有字段视为可信。

### 7.3 任务和工作单元

`CollectionTask` 保存原始请求、解析后的意图、计划、工作单元、公司名候选、地图候选、最终结果、相关性判断、摘要、checkpoint 和错误列表。`CollectionWorkUnit` 保存城市、关键词、Provider、模型、状态、候选统计、相关性统计、联系方式统计、重试次数和错误。

这是一个“聚合根加子实体”的设计。任务是用户可见的整体，工作单元是执行和恢复的最小边界。摘要可以从子实体重新计算，避免只依赖前端自己累加。

### 7.4 持久化表

`storage/models.py` 定义任务、候选、Lead、checkpoint、交付台账、批量任务、采集任务、工作单元、采集候选、采集 checkpoint 和结果消费记录等表。Repository 对外提供 `save`、`get`、`list`、`record_delivery`、`claim_result_consumption` 等操作。

默认使用 SQLite，适合本地或内网样片部署；SQLAlchemy 的 Repository 边界让未来切换到更强的关系型数据库时，业务服务不需要直接改成 SQL。项目当前的关键不是数据库规模，而是持久化状态和幂等记录不能随着进程重启丢失。

## 9. 标准化、去重和合并逻辑

### 8.1 为什么要标准化

同一个手机号可能有空格、短横线、国家码或括号；邮箱可能有大小写差异；公司名称可能有多余空格、全角符号、括号和“有限公司”格式差异。如果直接字符串比较，会产生大量重复。

`domain/normalization.py` 提供手机号、电话、邮箱、微信和公司名称的标准化函数。手机号会去除非数字字符，并检查移动号模式；固定电话单独处理，不和手机混淆；邮箱统一大小写和空白；公司名称用于身份比较时会清理符号和常见格式噪声。

### 8.2 公司身份和联系人身份

`domain/dedup.py` 计算公司身份、联系方式身份和稳定 payload fingerprint。公司身份通常结合规范化公司名和城市，避免同名企业在不同城市误合并；联系方式身份则用规范化后的手机号或其他主键识别重复。

跨关键词命中同一家公司时，系统优先保留一个候选，并追加新的来源 URL、证据引用和相关性判断。跨任务的结果消费还会结合 account scope 和结果指纹，保证一个下游账号不会重复领取同一有效结果。

### 8.3 合并优先级

合并时的基本原则是：来源明确且可信的字段优先；非空值优先于空值；地图核心字段不能被模型猜测覆盖；多个来源的 URL 和引用做稳定去重；冲突时保留审计信息而不是悄悄覆盖。这样即使模型在一次调用中返回不准确内容，也不会破坏已有的地图事实。

## 10. 交付与幂等设计

### 9.1 为什么投递需要门禁

ERP 投递属于外部副作用。把错误手机号或没有来源的联系人投递出去，影响比页面显示一条不完整结果更大。因此项目将“能展示”和“能自动投递”分成两个层级。

默认自动投递要求请求中需要的联系方式已经满足，并且对应字段有证据；没有独立验证的模型结果只能 `display_only`。验证型自动投递 `verified_auto_deliver` 还要求联系人证据满足更严格条件，例如手机号必须从地图详情中捕获并与公司精确匹配。

### 9.2 ERP Adapter

`providers/erp.py` 实现 `ErpHttpAdapter`。它根据 LeadRecord 构造规范化 payload，分离手机和座机字段，映射联系人类型，记录采集时间、来源 URL、证据引用等元数据，并通过 HTTP 发送到配置的 ERP 地址。真实 ERP 地址和 Bearer Token 来自配置或用户在工作台中输入的交付目标。

### 9.3 投递指纹和台账

系统用 payload 的稳定字段计算 fingerprint。发送前先查询交付台账，如果已经成功投递同一个指纹，就返回 `duplicate`，不再次发送；失败则记录错误、操作 ID 和尝试次数，允许用户重试。任务恢复后，台账仍然存在，所以不会因为服务重启而重复投递。

单条投递和批量投递使用同样的指纹思想。批量投递过程中，每条结果独立记录成功或失败，最终返回 sent、failed 和每条 Lead 的 DeliveryResult。前端因此可以只重试失败项，而不需要重新发送全部结果。

## 11. Connector 接口与安全边界

项目还有一个面向外部调用方的 connector 层。它通过 `connector/contracts.py` 定义稳定的健康状态、任务摘要、结果项、搜索请求和控制请求，通过 `connector/service.py` 把内部任务能力包装成外部更容易使用的接口。

Connector 不直接接收 ERP URL 或 Token，避免外部调用方借此改变服务端的投递配置。任务和结果还会按可信的 account scope 隔离，外部调用方只能看到自己的任务和结果。结果消费使用数据库中的 claim 记录做一次性领取，避免两个并发调用同时得到同一条线索。

对外返回的任务摘要会隐藏原始自然语言请求和敏感联系方式，只有适合外部消费的字段被暴露。面试中可以把这部分总结为：内部工作台偏运维和全量观测，Connector 偏稳定能力和最小数据暴露。

## 12. 前端工作台的实现逻辑

前端是一个任务工作台，不是静态展示页。用户可以输入自然语言，选择模型，配置是否连续采集、是否自动交付，创建任务后看到解析出的城市范围、关键词、工作单元数量和目标数量。

点击开始后，前端调用启动 API，并通过定时获取任务详情更新状态。状态由后端统一产生，例如 `planned`、`queued`、`running`、`paused`、`needs_attention`、`completed`、`completed_with_errors` 和 `cancelled`。前端的 `labels.ts` 只负责将状态转换为中文文案、说明和视觉色调，不在前端复制状态机。

工作台会显示：

- 当前任务状态和总体进度。
- 城市、关键词、工作单元完成数。
- 候选数、相关企业数、需要复核数。
- 有效联系方式数、无手机数、拒绝数。
- ERP 成功和失败数。
- 当前工作单元、错误原因和浏览器人工处理状态。
- 结果表格中的公司名、手机、地址、名称来源、地图来源和交付按钮。

结果表格将“来源渠道”和“打开地图”保留给用户，便于人工抽查；交付按钮会根据 URL 是否填写、手机是否有效、当前交付状态和失败原因决定是否可用。这样前端可以阻止明显无效的操作，但最终门禁仍然在后端再次执行。

旧版单公司和批量工作台也复用相同的 API 封装。`api.ts` 的 `request` 函数统一处理 JSON、HTTP 错误和后端 detail，业务函数只负责路径和请求体，减少组件内重复 fetch。

## 13. 异常处理与可恢复性

### 12.1 异常分类

项目没有把所有异常都当成一个普通字符串，而是区分：

- 外部服务配置错误，例如地图 Key 缺失、ERP URL 未配置。
- 网络或页面超时，可以重试。
- 登录状态缺失，需要人工处理。
- 安全挑战，需要人工处理。
- 模型响应格式错误，可以保留候选并重试补全。
- 业务校验失败，例如城市不匹配、公司名不精确、手机号无效。
- 数据库或持久化错误，需要任务进入错误状态并保留上下文。

不同错误对应不同策略。可重试错误记录 retry_count 和 retry_after；登录和 challenge 让任务进入 needs_attention；业务拒绝记录候选被拒绝原因但不把它当作系统崩溃；部分工作单元失败则最终进入 completed_with_errors。

### 12.2 暂停、恢复、取消

暂停不是简单设置一个布尔值。服务层会在工作单元边界以及浏览器操作返回后检查暂停事件，安全停止当前循环，保存当前 checkpoint，并把任务置为 paused。恢复时跳过已成功工作单元，重新打开或连接专用浏览器，继续未完成单元。

取消是终态，取消后的任务不能继续恢复，避免后台 worker 已经退出但 UI 仍然把它当成可执行任务。连续采集还会处理“暂停后第二天继续”的场景，按日期重置每日有效结果统计，避免旧日期进度错误地阻止新一轮采集。

### 12.3 进程重启

任务状态保存到 SQLite。应用启动时会构建 Runtime Components，恢复 Repository、Provider、浏览器和服务；读取任务时会重新计算必要摘要，并对上次进程退出时停留在 running 的任务进行修正，避免数据库一直显示一个没有 worker 的运行状态。

浏览器状态和业务状态分离。进程重启后浏览器可能已经关闭，任务不会假设页面还存在，而是根据 checkpoint 尝试重连；如果需要登录，则返回明确的人工处理状态。

## 14. Provider 抽象为什么重要

地图 Web 自动化会受到页面 DOM、登录和安全策略影响；地图 API 需要 Key 和配额；模型网页需要登录；模型供应商也可能更换。如果业务服务直接调用这些具体实现，后续替换 Provider 会牵动整个任务流程。

项目用 Protocol 定义能力：地图发现、模型补全、地图证据验证、公开网页证据、ERP 交付。`registry.py` 根据 Provider ID 构建真实实现；测试环境注入 Fake Provider。Collection Service 只面对统一方法和领域对象，因此可以在不启动浏览器、不联网、不调用模型的情况下测试绝大多数业务规则。

这也带来清晰的测试边界：Provider 测试关注页面解析、API 映射和模型响应解析；Domain 测试关注标准化、去重、合并和证据门禁；Service 测试关注任务编排、恢复、限制和交付；API 测试关注路由、状态码和响应结构。

## 15. 测试覆盖和质量保证

后端依赖 Pytest、pytest-asyncio、pytest-cov 和 Ruff。测试目录按 api、batch、collection、domain、providers、services、storage 等划分。

领域层测试包括手机号和公司名称标准化、公司与联系人身份、候选和补全合并、任务状态转移、证据门禁。采集服务测试覆盖真实公司名发现、跨任务去重、跨工作单元去重、城市限制、源耗尽、精确地图匹配、跨城市误匹配、住宅无关结果排除、地图手机优先、座机不能作为有效手机、暂停恢复、取消、重试、连续采集和重新加载。

面试时不建议只说“有单元测试”。更好的说法是：

> 我们用 Fake Provider 把外部依赖隔离开，重点测试业务不变量，比如同一个手机号只算一个有效线索、座机不能满足手机条件、没有证据的模型字段不能自动投递、暂停恢复不能重复执行成功工作单元、投递指纹能防止重复发送。对于网页和 API 适配器，再单独测试解析与映射。

## 16. 项目中最值得讲的工程难点

### 难点一：地图搜索结果不等于目标企业

宽泛关键词会得到大量噪声，直接采集会产生楼宇、门店、商圈和同名错误结果。解决方式是“先发现公司名，再用公司名和城市做精确查询”，并在最终入库前做名称匹配、城市匹配和类别判断。关键词搜索是召回，精确 POI 是确认，模型判断是相关性过滤，三层组合比单次搜索可靠。

### 难点二：浏览器自动化天然不稳定

地图页面可能慢、断开、需要登录或触发挑战。项目把浏览器生命周期、页面操作、超时替换、重连和暂停诊断独立封装；把登录和 challenge 建模为业务状态；通过 checkpoint 让恢复不是从头开始。这个设计把外部不确定性控制在 Provider 和浏览器边界内。

### 难点三：模型不能直接产生可信数据

模型可能幻觉、返回 Markdown、输出错误 JSON 或把座机当手机。项目使用结构化 Prompt 和 Parser，检查公司名、字段类型、未知标记、有效手机号和来源；再通过证据系统决定字段状态。模型的角色是提取和判断，可信度来自来源证据和业务门禁。

### 难点四：长任务需要中断恢复

一个任务可能包含很多城市和关键词，不能只在内存里保存进度。项目将任务拆成工作单元，每个单元独立保存状态、统计、失败原因和重试时间；checkpoint 保存当前边界；成功单元恢复后跳过，失败单元可单独重试。这样进程重启、浏览器登录、暂时网络错误都不会导致全量重跑。

### 难点五：重复数据和重复副作用

同一公司可能命中多个关键词，同一手机可能出现在多个来源，同一个 ERP payload 可能因为页面刷新被再次点击。项目使用标准化身份、来源合并、稳定 ID、交付 fingerprint 和 delivery ledger，分别解决结果重复和副作用重复。

### 难点六：业务状态和展示状态容易混淆

“抓到了一个号码”“号码有公开来源”“号码已经独立验证”“号码可以投递”是四个不同事实。项目用 EvidenceValue 和 DeliveryResult 把它们拆开，前端显示捕获、来源支持、已验证、仅展示、已投递、重复和失败等状态，避免用户误以为所有展示数据都能直接进入 ERP。

## 17. 一次完整请求的面试讲法

当面试官问“详细说一下项目流程”，可以按下面的顺序回答：

第一步，前端把用户输入的自然语言和采集选项提交到自然语言创建接口。后端先解析意图，不会立即产生外部搜索副作用。

第二步，意图解析器识别城市、行业关键词、联系方式、数量和模型；对于住宅装修等业务扩展关键词，过滤无关词并设置目标有效手机号数量。

第三步，Planner 根据城市和关键词生成稳定 ID 的工作单元，每个工作单元都是一个可以单独运行和恢复的执行边界，任务计划持久化后才允许启动。

第四步，服务逐个运行工作单元。先从公开网页或地图关键词结果发现真实公司名，再跳过已在其他任务中处理过的企业，使用“公司名加城市”进行地图精确查询。

第五步，Provider 将地图网页或 API 结果统一转换成 MapPoiCandidate，核心服务检查名称、城市和 POI 详情，拒绝模糊匹配和位置类 POI。

第六步，对候选企业做相关性判断。模型输出会经过 Parser，保存状态、理由、置信度和模型 ID；无关和需要复核的候选不会直接进入有效结果。

第七步，对相关企业做信息补全，并把地图字段、公开网页字段和模型字段按优先级合并到 LeadRecord。地图详情中的真实手机优先于模型猜测，座机单独保存。

第八步，证据验证器检查字段来源和引用，更新字段级证据状态。只有满足用户联系方式要求且证据达到投递门槛的结果，才可以自动投递。

第九步，系统按规范化公司和手机号去重，更新城市限制、有效联系方式统计和任务完成原因。达到目标就停止后续工作单元，所有来源耗尽则以 source_exhausted 完成。

第十步，ERP Adapter 构造标准 payload，生成 fingerprint，先查投递台账再发送。重复 payload 返回 duplicate，失败记录原因并支持重试，成功结果可以安全恢复和查询。

最后，前端持续查询任务详情，显示工作单元、摘要、证据和交付状态；遇到登录或安全验证时提示用户在专用 Chrome 中人工处理，然后点击恢复。

## 18. 常见面试追问与回答

### 问：为什么不直接把自然语言交给大模型解析？

答：涉及城市、数量、联系方式和交付条件的字段需要稳定和可测试。项目用规则提取确定性较强的部分，用固定扩展矩阵和可选模型建议处理关键词变体。这样同一句输入在不同时间不会因为模型随机性产生完全不同的城市或数量，也能用单元测试覆盖边界。模型更适合处理相关性和公开文本信息，而不是承担所有业务控制逻辑。

### 问：为什么要先搜索公司名再查地图？

答：行业关键词搜索召回量大但噪声多，可能没有真实公司全称。先发现公开出现的公司名，再用公司名和城市精确查询，可以把召回和确认分离。地图详情提供最终 POI、地址和电话；公开网页负责扩大公司名召回和补充证据。两阶段更容易解释，也减少错误 POI。

### 问：为什么使用浏览器自动化而不是纯 HTTP？

答：当前地图页面的可见数据和用户登录状态是采集条件，某些页面操作不能稳定地通过公开 HTTP 接口完成。Playwright 通过 CDP 操作专用 Chrome，可以复用登录状态并让人工处理安全验证。代码把页面操作隔离在 Provider，未来如果 API Provider 足够稳定，可以通过配置切换而不修改业务服务。

### 问：如果浏览器卡住怎么办？

答：浏览器操作有超时，Browser Actor 能替换超时 worker；Provider 记录失败和浏览器状态；服务层根据异常类型决定重试或暂停。登录和安全验证不会无限重试，而是进入 needs_attention。任务已经保存工作单元和 checkpoint，所以恢复时跳过已成功部分。

### 问：模型返回了一个手机号，为什么不能直接用？

答：模型可能推测或产生幻觉。Parser 会过滤未知和猜测标记，证据模型记录字段来源。默认只能展示没有证据的字段，自动交付要求字段级证据满足门禁；验证型自动交付还要求独立证据或地图详情捕获。这样把模型输出和真实业务数据分开。

### 问：如何保证不会重复投递？

答：发送前根据稳定 payload 计算 fingerprint，查询 delivery ledger；已成功的指纹直接返回 duplicate，不再次调用 ERP。发送失败记录 attempts、error 和 operation_id，重试时仍使用同一指纹。数据库台账保证进程重启和重复点击也不会产生重复副作用。

### 问：暂停恢复会不会重复搜索？

答：工作单元状态和 checkpoint 持久化。恢复时已经 succeeded 的单元会跳过；同一公司名在其他任务或更早单元已经成功精确查询的，也会通过公司身份和搜索记录跳过。即使某个单元中后半段失败，候选和成功的 Lead 也会保留，不会因为整体失败而全部丢弃。

### 问：为什么 SQLite 足够吗？

答：项目当前定位是本地或内网部署样片，SQLite 足够承载任务状态、候选、结果和台账，部署成本低。更重要的是 Repository 抽象和 ORM 表结构已经把持久化边界隔离开；如果进入多实例、高并发生产环境，可以迁移到 PostgreSQL，并进一步把后台执行和浏览器会话拆成队列 worker。SQLite 是当前部署约束下的合理选择，不代表架构只能停留在 SQLite。

### 问：如果要上线，你会怎么改进？

答：首先把 SQLite 切换到 PostgreSQL，并把后台任务从进程内线程迁移到可靠队列；其次给 Provider 增加配额、限速、熔断和更细的可观测指标；再次把浏览器执行器独立成有生命周期管理的 worker，任务状态通过消息和数据库协调；然后完善权限、敏感字段脱敏、审计日志和 ERP 重试策略。业务层的工作单元、证据和指纹设计可以继续复用。

## 19. 从零上手项目的阅读顺序

完全不了解项目时，不建议一开始就看地图选择器。推荐按下面的顺序理解：

1. 先读 README，知道项目运行方式、默认端口、浏览器 profile 和 Provider 配置。
2. 再看 `frontend/src/types.ts`，从前端类型理解任务、工作单元、Lead、证据和投递状态。
3. 读 `backend/app/domain/models.py`，理解 Candidate、Lead、EvidenceValue 和 DeliveryResult 的边界。
4. 读 `backend/app/collection/intent.py` 和 `planner.py`，明白自然语言如何变成工作单元。
5. 读 `backend/app/collection/service.py` 的公开方法和执行流程，理解主业务编排。
6. 再读 `providers/protocols.py`，把地图、模型、证据和 ERP 的接口与具体实现分开。
7. 读 `providers/amap_web.py`、`amap_api.py`、`doubao_web.py` 和 `public_web.py`，了解外部系统差异。
8. 读 `domain/normalization.py`、`dedup.py`、`merge.py`、`evidence.py`，理解数据质量规则。
9. 读 `storage/repositories.py` 和 `storage/models.py`，理解如何保存和恢复任务。
10. 最后读 API 路由、前端 `CollectionWorkbench.tsx` 和测试，建立端到端对应关系。

阅读每个文件时可以问三个问题：输入是什么，输出是什么，失败后谁负责处理。能回答这三个问题，就能快速定位大多数逻辑。

## 21. 项目价值和最终总结

项目的核心价值是把一个依赖人工经验的地图获客流程，抽象成了可编排的、可恢复的、带证据的任务系统。它有明确的输入模型、计划模型、执行单元、领域数据模型、Provider 接口、持久化 checkpoint 和交付台账。

从业务角度看，用户只需要描述“去哪里找什么企业、需要什么联系方式、要多少条”，系统就能给出可检查的采集计划和进度。从工程角度看，外部网页、浏览器、模型和 ERP 都是不稳定或有副作用的依赖，因此项目重点不是写一个大循环，而是把不确定性隔离、把状态保存、把错误分类、把来源记录下来。

最值得在面试中强调的不是“用了哪些库”，而是以下几条设计判断：

- 用规则和模型结合处理自然语言，确定性字段不完全依赖模型。
- 用“公司名发现加地图精确确认”解决宽泛搜索噪声。
- 用 Provider Protocol 隔离地图、模型、网页和 ERP 的变化。
- 用工作单元和 checkpoint 支持长任务暂停、恢复和局部重试。
- 用标准化、身份指纹和合并策略解决跨关键词重复。
- 用字段级证据和交付门禁防止未经验证的数据进入 ERP。
- 用 delivery ledger 和 fingerprint 保证外部副作用幂等。
- 用 Fake Provider 和分层测试验证业务不变量，而不是依赖真实网页才能测试。

如果需要用一段 30 秒的话收尾，可以说：

> 这个项目最核心的不是把地图搜索自动化，而是把外部数据采集做成一个可靠的业务工作流。我们将自然语言需求拆成稳定的城市关键词工作单元，使用多 Provider 发现和确认企业，利用证据模型控制数据可信度，再通过 checkpoint、重试和投递台账保证长任务与外部副作用可恢复、可审计、不可重复。这样系统既能提升获客效率，也能让业务人员知道每条线索从哪里来、为什么有效、是否可以投递。

| 前端类型 | `frontend/src/types.ts` | 任务、结果、证据和投递类型 |
| 采集工作台 | `frontend/src/CollectionWorkbench.tsx` | 输入、进度、结果和控制操作 |
| 测试 | `backend/tests`、`frontend/src/*.test.ts` | 业务不变量和接口行为 |

## 22. 深入实现说明：从代码结构到工程决策

前面的章节已经说明了系统“做什么”。本章进一步解释“代码到底怎样把它做出来”，特别适合面试前复习。阅读这部分时可以把系统理解为一条受控流水线：输入并不直接生成结果，而是不断在不同的状态、模型和证据之间转换。每一步都要明确输入、输出、失败条件和持久化位置。

### 22.1 应用启动与依赖装配

后端入口在 `backend/app/main.py`。应用启动时不会在路由函数里临时创建数据库连接、浏览器或 Provider，而是由 `runtime.py` 统一构建 Runtime Components。这个运行时对象相当于应用的依赖容器：它持有数据库 session factory、任务 Repository、Collection Service、单公司 Search Service、BatchJobManager、地图 Provider、模型 Gateway、证据验证器、ERP Adapter 和浏览器实例。

这样做有三个好处。第一，依赖关系集中。开发者想知道“自然语言采集到底使用哪个地图 Provider、哪个模型、哪个数据库”，只需要从 runtime 装配代码追踪，不需要在几十个 API 函数中搜索。第二，测试容易替换。测试可以把真实 AmapWebProvider 换成 FakeMapDiscoveryProvider，把真实 ERP Adapter 换成内存 Adapter，不访问网络也能验证业务流程。第三，生命周期清楚。应用关闭时，运行时统一关闭浏览器、后台 manager 和数据库相关资源，避免 Playwright 进程或 worker 泄漏。

配置由 `config.py` 中的 Settings 负责。它会读取环境变量和 `.env`，并为端口、数据库路径、超时、重试次数、地图 Key、ERP 地址等提供类型化默认值。配置与业务逻辑分离是必要的：本地开发、演示环境和正式环境使用不同 API Key、浏览器端口或 ERP 地址时，不需要改代码，也避免凭证写死进仓库。

面试表达可以是：

> 我把外部依赖放进运行时装配层，而不是让业务服务自己 new 浏览器或 HTTP 客户端。这样 Provider 可以通过配置切换，测试可以注入 Fake 实现，应用关闭时也能统一释放资源。它本质上是轻量的依赖注入，不依赖复杂框架但边界清楚。

### 22.2 HTTP API 如何设计

路由层分为 `routes.py`、`collection_routes.py` 和 `connector_routes.py`。三者面对的用户不同：普通任务 API 面向工作台；Collection API 面向自然语言采集；Connector API 面向外部系统集成。虽然都使用 FastAPI，但职责不同，因此不要把所有接口混在一个文件里。

创建接口通常遵循“先声明，再执行”的原则。以自然语言采集为例，创建接口返回已经解析的意图和计划，而不是立刻搜索。这让页面能展示城市、关键词和工作单元数，用户确认后再调用 start。这个设计还提高了可测试性：测试创建接口时不需要启动浏览器，也不会意外产生第三方请求。

控制接口使用显式动词：`start`、`pause`、`resume`、`cancel`、`retry-errors`、`deliver`。这种设计比一个包含复杂 action 参数的接口更容易读，也更容易针对每种动作设置状态校验。比如取消后的任务不能 resume；暂停中的任务才允许恢复；只有包含有效手机的结果才允许单条投递。路由负责把错误转换为明确的 HTTP detail，服务层负责判断业务状态是否允许转移。

返回对象不是数据库 ORM 行，而是领域模型或专门的响应模型。前端得到的是 `CollectionTask`、`LeadRecord`、`DeliveryResult` 等稳定结构，不会感知 SQLAlchemy 内部字段。这个边界避免数据库设计变化直接破坏前端，也能在 Connector 场景下输出经过脱敏和筛选的摘要模型。

### 22.3 状态机：为什么不用一个 running 布尔值

长任务的状态不是“运行或不运行”这么简单。单公司任务有 created、discovering_map、candidates_ready、enriching_doubao、verifying、ready、delivering、completed、paused、waiting_for_login、waiting_for_challenge、completed_with_errors 等状态；自然语言任务有 planned、queued、running、paused、needs_attention、completed、completed_with_errors、cancelled；工作单元又有 planned、running、succeeded、no_result、skipped_limit、retry_wait、needs_attention、failed、paused 等状态。

状态细分的价值是让系统能回答具体问题：任务没开始，是用户还没有确认还是正在排队？任务没继续，是网络超时、模型失败、登录失效，还是触发安全验证？任务结束，是已经达到 100 个有效手机号，还是所有来源找完了？这些不是 UI 文案差异，而是不同恢复策略。

`domain/task_state.py` 将单公司状态转移集中管理。服务不应该随意写 `task.status = 'completed'`，而应该通过转移函数确保状态合法。例如从暂停恢复可以回到发现或补全阶段，但 cancelled 不可恢复；处于登录等待的任务必须在用户处理浏览器后才应继续。集中状态机也让测试可以直接验证非法转移。

Collection Task 的 checkpoint 负责保存“在状态中的位置”。它包含当前阶段、当前工作单元 ID、已完成和失败单元、浏览器状态、下次重试时间，以及联系人刷新任务的索引。只保存状态名不足以恢复，因为系统还需要知道从哪一条继续。把位置持久化后，恢复不依赖内存，也不依赖“重新跑一遍再猜哪里完成过”。

### 22.4 异步执行和并发边界

项目中的采集是长耗时操作，但 API 请求不能一直阻塞到所有城市完成。因此服务提供 `start_async`、`resume_async` 等入口，后台执行器负责运行任务，API 很快返回当前任务状态。前端轮询任务详情或列表，持续呈现进度。

这里要区分“任务可以并发”和“一个浏览器页面可以并发”。业务上可以有多个任务，但同一个专用 Chrome/CDP 会话不适合被多个协程同时输入关键词、点击结果、等待详情。如果多个任务共享一个页面，A 任务可能在等待详情时被 B 任务改写搜索框，导致结果串台。项目用 Browser Actor 将页面命令串行化，把浏览器视为受限资源；工作单元在服务层排队执行，而不是盲目提高并发。

这种选择体现了吞吐量与正确性的取舍。对地图网页采集来说，错误页面和错误企业的代价高于少量吞吐量损失。未来如果要提高吞吐量，正确方案是创建多个独立浏览器 worker 和 profile，并用任务队列分配，而不是让多个线程同时操作一个 Page。

### 22.5 高德网页 Provider 的处理细节

`AmapWebProvider` 将网页搜索封装为 `search_company` 和 `search_keyword` 两类能力。前者接受公司全称和城市，用于最终精确确认；后者接受行业关键词和城市，用于发现候选。两者都复用内部搜索流程，但用途不同，服务层也用不同的质量门槛处理返回结果。

页面层的 `AmapPageAdapter` 负责寻找搜索输入框、提交查询、等待结果卡片、读取卡片文本、打开详情链接、从详情面板获取电话和地址。页面元素选择器、等待逻辑、URL 判断和可见文本清理都留在 adapter 内，而不是散落在 Collection Service。这样网页 DOM 调整时，改动范围局限在 Provider。

等待策略不是单纯 `sleep`。代码会轮询结果卡片和页面文本，并识别“无结果”、加载超时、登录页、验证页等状态。对搜索动作还会做节奏控制和随机延迟采样，避免短时间高频操作导致页面不稳定或安全策略更容易触发。这里的目标不是绕过网站策略，而是在允许的人工登录和正常使用条件下，减少无意义的瞬时重复请求。

打开详情页时，系统会核对详情 URL 和页面文本是否仍然对应目标公司。原因是地图界面可能复用面板、异步刷新或打开新标签，不能只因为“点了一次结果”就假设当前页面一定是那个 POI。候选中会保存 POI ID、详情 URL、原始可见文本和来源元数据，既支持后续证据解释，也方便定位页面解析问题。

### 22.6 地图 API Provider 与网页 Provider 的统一

网页采集和地图 API 的返回结构不相同：网页是卡片和详情文本，API 是 JSON POI 数组。若直接把两种响应传入业务代码，Collection Service 会被大量 `if provider == ...` 分支污染。

项目通过 Provider Protocol 统一抽象。AmapApiProvider 将 API 响应解析成 `MapPoiCandidate`，统一填充公司名、城市、地址、电话、坐标、POI ID、来源 URL 和 raw metadata；AmapWebProvider 也返回同一个模型。业务层只消费 Candidate，不关心它来自 DOM 还是 JSON。

这不仅是面向接口编程的形式要求，还解决了数据语义一致性问题。例如 `mobile` 始终表示已识别的移动号码，固定电话放 `telephone`；`source_urls` 始终是证据来源集合；`discovery_channel` 标记来源。只有统一语义，后面的去重、验证和投递门禁才不需要按 Provider 重写。

### 22.7 模型提示词与响应解析的双重约束

模型部分最容易被误解为“给公司名，模型返回联系人”。实际实现有两层约束。第一层是 Prompt：补全、相关性判断、关键词建议分别使用不同 prompt builder，明确输入上下文、要求 JSON 格式、列出允许字段，并要求对不确定信息返回空而不是猜测。第二层是 Parser：`doubao_parser.py` 并不相信模型一定遵守格式。

Parser 会先尝试从 Markdown、代码块或自然语言里提取 JSON，再检查结果是否为对象、状态值是否属于允许集合、公司名是否匹配当前查询、来源 URL 是否是有效链接、号码是否满足手机格式。对“可能是”“猜测”“未知”“暂无”等标记，代码不会把它作为真实值。解析后的 `DoubaoEnrichment` 是受控数据结构，而不是原始模型文本。

相关性模型输出也保留 reason 与 confidence。reason 让用户知道为什么企业被判断相关或无关；confidence 不能单独替代证据，但可帮助运营排序人工复核项。模型失败时，候选不会被删除，工作单元记录可重试错误。这个策略避免一次模型短暂不可用导致前面昂贵的地图发现结果丢失。

### 22.8 公开网页证据为什么要单独存在

地图页面可以提供 POI 和联系方式，但并不总能确认联系人、邮箱或微信。公开网页证据 Provider 的目标不是无限爬取互联网，而是在有限、可解释的来源中核对“该公司与该联系方式是否同时出现”。

实现上，Provider 使用 HTTP 获取候选页面或搜索结果，再用 HTMLParser 提取可见文本，避免把脚本、样式和隐藏结构直接当成业务文本。它会寻找公司名称和预期联系方式，构造包含匹配值的短引用，并返回 URL、quote、字段状态和分级。若只能找到公司但找不到号码，不会错误标记为联系方式已验证。

这是一种来源可追溯设计。用户在结果表中能打开来源页面，开发者能看到 evidence quote，系统能解释“手机号为什么可以投递”。相比只存 `verified=true`，可追溯证据更容易排错，也更适合面对业务审计。

### 22.9 字段级证据与投递门禁的具体关系

系统将数据可信度分层：`captured` 表示从某个页面或接口获得；`source_backed` 表示有可复查来源支撑；`verified` 表示满足更严格的交叉或独立验证条件。Lead 顶层还保存公司名验证状态、联系人验证状态、证据 URL、引用、分级和分数。

投递前，`domain/evidence.py` 中的门禁会综合请求的联系方式要求、字段是否为空、字段证据状态、公司名状态、来源 URL 以及是否已经交付来产生 Delivery Decision。决策可能是 `ready` 或 `display_only`，并带 reasons，例如公司名未验证、联系方式未验证、缺少手机或邮箱、缺少来源 URL、payload 重复。

这里的关键是“展示不等于投递”。很多采集产品把结果一律写入库，业务人员很难知道哪个数字来自网页、哪个数字来自模型。该项目明确允许把低证据结果展示给用户作为线索，但自动化下游动作只接受达到门槛的数据。前端也会根据后端 reasons 禁用或提示投递按钮，但后端仍做最终校验，防止绕过 UI 直接调 API。

### 22.10 Repository 如何保障任务恢复

业务服务面对的是 Pydantic 模型，Repository 才面对 SQLAlchemy Session 和 ORM Row。保存一个 CollectionTask 时，Repository 不仅保存任务基本字段，也保存 work units、公司名候选、地图候选、结果、相关性决策、checkpoint 和交付记录相关信息。读取时再恢复为领域对象。

这种映射看起来工作量较大，但对长任务非常必要。若只把最终结果保存到一张表，服务重启后就不知道哪些关键词已执行、哪个单元是等待登录、哪些失败需要重试、当前有效手机号数量如何计算。项目将过程数据也持久化，换取可恢复性和可观测性。

数据库中还有 DeliveryLedger 和 ResultConsumption 等记录。前者保证同一 ERP payload 的幂等，后者服务于 Connector 的结果一次性领取。`claim_result_consumption` 的语义是“检查并占用”而不是先查再写，避免两个并发请求同时看到未消费然后各自返回同一条线索。

### 22.11 统计指标如何计算

Collection Summary 包含总工作单元、完成单元、候选数、相关数、复核数、联系方式数、验证数、ERP 成功和失败数、目标有效手机号、实际有效手机号、无手机号数、拒绝数和来源是否耗尽。

这些数字不能只由前端累加，因为刷新页面、暂停恢复或任务重载后会丢失前端状态。服务层根据持久化的工作单元、候选、结果和交付状态重新刷新摘要。有效手机号统计会先标准化，再按唯一电话号码去重，并保证只有地图详情捕获或满足证据要求的号码计入目标。无手机号、拒绝和失败也作为独立指标出现，避免把“结果少”误解为“系统没有执行”。

指标不仅用于仪表盘，也参与控制流。达到 target_valid_contacts 时，服务会停止后续不必要的工作单元；达到单城市限制时，剩余单元标记 skipped_limit；所有可执行来源结束后，设置 source_exhausted。也就是说，统计是业务决策输入，不只是展示数据。

### 22.12 批处理导入的细节

批量文件导入首先是数据质量问题，而不是任务队列问题。`CompanyInputImporter` 支持 CSV 与 XLSX，CSV 按 UTF-8 读取，XLSX 使用 OpenPyXL。导入器会标准化表头，识别“公司名称”和“城市”这种常见列名变体，检查必填列，逐行记录错误位置，并在进入执行队列前基于公司身份去重。

为什么要在导入时就做这些？因为一千行 Excel 在执行到第 900 行才发现表头错误，用户的等待成本很高；同一公司多次出现会浪费地图查询和模型调用；空城市会让精确地图匹配失去约束。导入阶段失败能够给用户明确的文件级问题，执行阶段只处理已经合法的 CompanyInput。

BatchJobManager 为每行创建 BatchItem，状态独立为 queued、running、completed 或 failed。成功项目保留关联任务 ID 和候选数，失败项目保留错误和重试次数。批量任务可以部分完成，不能因为一行名称有问题而回滚前面所有成功项。这是典型的长批处理“逐项容错、最终汇总”设计。

### 22.13 前端状态管理与轮询

前端没有引入重量级全局状态库，当前工作台的状态范围主要在单个 React 页面内：请求文本、模型选择、任务列表、当前任务、busy 操作标志、过滤条件、交付地址和 token、提示消息。对这类内部工具，局部 `useState` 和明确的 API 调用比过早引入复杂 store 更容易维护。

创建和控制操作都使用 `busy` 标识，防止用户在一次 start、pause 或 deliver 尚未返回时重复点击。任务执行中，工作台通过获取任务详情刷新数据；当前任务状态进入终态后停止不必要轮询。列表与详情分开获取，既能显示历史任务队列，也能让当前任务呈现足够完整的结果和错误信息。

TypeScript 类型是前后端契约的第一道保护。比如 CollectionWorkUnitStatus、DeliveryResult.status、EvidenceValue.status 都写成联合类型，组件不应该把任意字符串当成状态。`labels.ts` 将状态映射到中文标签和色调，避免在多个组件复制一组容易不一致的 if/else。

### 22.14 测试策略为何分层

项目面对的外部依赖很多：浏览器、地图、模型、公开网页、ERP、文件系统和数据库。如果每个测试都走真实链路，会慢、不稳定、需要账号，还可能触发真实投递。因此测试首先验证不变量，而不是验证某个页面今天是否可访问。

Domain 测试最快，验证手机号归类、公司名身份、payload fingerprint、候选合并、证据门禁和状态迁移。Service 测试用 Fake Provider 组合出成功、无结果、超时、登录等待、座机、跨城市错误匹配、模型失败等场景，验证编排和恢复。Repository 测试验证保存读取后字段不丢失。API 测试验证 HTTP 入口的请求校验、状态码和返回结构。Provider 测试才针对 API 映射、网页解析器或浏览器生命周期。

这种金字塔能让大部分回归在本地快速发现。例如“座机不能被当作手机”不需要打开地图网页；“重复投递必须返回 duplicate”不需要真实 ERP；“暂停恢复不应重跑成功单元”不需要真实模型。真实环境验证仍然重要，但它用于检查账号、页面变化、网络和配额，而不是承担全部逻辑测试。

### 22.15 典型问题与处理方式复盘

问题一：地图关键词搜索返回看似相关、实际不是公司本身的地点。处理方式是将关键词搜索定位为公司名发现，最终必须经过公司名加城市的精确搜索，名称和城市不满足时拒绝。

问题二：同一公司被不同关键词、多次公开搜索或不同任务发现。处理方式是对公司名和城市计算身份，对来源 URL 和引用做集合合并；更早已搜索过的企业不重复精确查询。

问题三：地图返回 400 电话、座机或者格式混乱的号码。处理方式是标准化时区分 mobile 与 telephone，只有合法移动号码才能计入有效手机号和走自动投递路径。

问题四：模型输出并非 JSON 或给出不匹配公司名。处理方式是 Parser 抽取 JSON 并校验字段、公司名和状态，失败保留为任务错误，允许重试，不将不可信文本落为有效字段。

问题五：浏览器要求登录或出现安全验证。处理方式是检测页面状态，将任务暂停为 needs_attention，保留 checkpoint，由用户在专用 Chrome 中处理后恢复，而不是无限重试。

问题六：网络或网页超时导致长任务中断。处理方式是工作单元级持久化、retry_count、retry_after 和后台恢复；成功结果先保存，重试只针对失败单元。

问题七：用户重复点击投递或服务重启后重新执行。处理方式是稳定 payload fingerprint 和数据库 delivery ledger，成功指纹直接返回 duplicate，失败记录重试上下文。

问题八：多个外部账号或调用方不应该相互看到和消费结果。处理方式是 Connector 引入 account scope，并在结果消费表中原子 claim，保证任务隔离和结果唯一分配。

### 22.16 当前方案的局限与下一阶段演进

项目当前明确适合单机、本地或内网环境。SQLite、进程内后台 worker 和单浏览器执行器换来了低部署成本和较短交付路径，但当任务量和用户数增长时会出现边界：SQLite 对多进程写入和高并发不理想；单浏览器是吞吐瓶颈；进程内任务在主进程故障时需要额外的守护与恢复；公开网页来源受页面变化和访问策略影响。

生产化演进应在保持领域模型不变的前提下替换基础设施。数据库可迁移到 PostgreSQL；任务执行可迁移到 Redis 加 Celery、RQ 或专用队列 worker；浏览器可以扩展为多个带独立 profile 的采集 worker；Provider 可以增加限流、熔断、健康检查、成功率指标和页面选择器版本监控；ERP 可以增加回调、死信队列和人工复核后台。

隐私与合规也应成为下一阶段的显式设计。应限制采集字段只服务于正当业务目的，对联系方式按角色脱敏，保留访问审计和来源说明，设置数据保留期限，并确保采集和交付符合来源平台规则与适用法律。当前项目中已有证据和来源记录基础，这有利于将来补充审计与合规模块。

### 22.17 面试中如何评价自己的贡献

如果面试官询问“你具体负责了什么”，可以不要泛泛回答“做了后端”。更有说服力的表达是：

> 我主要负责把地图获客需求抽象成可恢复的任务工作流。具体包括自然语言意图解析和城市关键词规划、地图与公开网页 Provider 的统一模型、任务状态与 checkpoint 持久化、企业和联系方式的标准化去重、模型输出的结构化校验、字段级证据门禁，以及 ERP 的幂等投递。前端侧我也定义了任务和结果类型，完成了工作台的状态展示和任务控制接口对接。实现时我重点控制了三类风险：外部网页不稳定、模型数据不可信、长任务可能重复执行或中断。

如果被追问“哪一部分最难”，选择一个真实问题展开即可，例如浏览器与恢复：

> 最难的是把浏览器异常从普通报错变成可恢复状态。地图网页会遇到超时、登录失效和安全验证，这些问题不能都靠重试解决。我将浏览器状态显式映射到任务状态，用 checkpoint 保存当前工作单元，并将页面操作串行化。这样用户处理登录后可以恢复，已经完成的单元不会重复跑，失败项也能单独重试。

这类回答有场景、有设计、有结果，比只说“我用了 Playwright”更能证明工程能力。

## 23. 技术选型与权衡：为什么使用这些技术

技术栈不是把流行框架堆在一起，而是要匹配项目的约束。MapSearch 的约束包括：开发期希望快速交付可运行的内网工具；任务包含 API、数据库、浏览器和模型等多种 I/O；需要大量结构化业务对象；依赖的地图网页不稳定；后台任务要保存状态；前端是给运营人员重复使用的工作台；真实外部账号在本地机器上更容易管理。理解这些约束后，选型就有了逻辑。

### 23.1 为什么选 Python 3.12

项目后端选择 Python 3.12，而不是 Java、Go 或 Node.js，首先是因为核心工作以数据处理、网页自动化、外部 API 编排和规则开发为主。Python 在这些领域有成熟生态：FastAPI 适合快速建立类型化 HTTP API，Playwright 提供完善的 Python 异步接口，Pydantic 能把外部 JSON、领域对象和配置统一为可校验模型，OpenPyXL 能处理 Excel，Pytest 便于通过 fixture 注入 Fake Provider。

Python 也适合将业务规则写得接近自然语言。例如解析城市、联系人、数量和关键词时，正则、数据类和列表去重逻辑可读性高；Pydantic 模型使 Candidate、Lead、Task、Evidence 的字段一目了然。对这类任务编排系统，开发正确性和演进速度往往比极限 CPU 吞吐更重要。

没有选择 Node.js 作为后端，不代表 Node 不适合，而是项目已经需要浏览器自动化、表格处理、数据校验和业务测试，Python 能将这些能力放在一个语言和测试体系内。没有选择 Go 的原因是当前外部等待时间远大于本地计算时间，Go 的并发优势并不是最先需要解决的问题；同时 Python 的业务迭代和分析工具更直接。未来若出现高并发 Connector 网关，也可以单独使用更高吞吐的服务，但不应在早期为了假设的性能拆散核心领域逻辑。

Python 3.12 的版本约束还具有工程意义。它固定了语法、类型行为和依赖兼容范围，避免本机、演示机和 CI 使用不同版本导致 Playwright、Pydantic 或 SQLAlchemy 行为不一致。README 的 Conda 启动方式也服务于这一目标：环境可复现，开发者不需要依赖全局 Python。

### 23.2 为什么选 FastAPI，而不是 Flask 或 Django

FastAPI 的优势是异步能力、类型提示集成、Pydantic 校验和自动 OpenAPI 文档。项目有多个 JSON API，既要接收自然语言任务、批量文件、控制操作，也要返回嵌套的任务、工作单元和证据模型。用 FastAPI 时，请求模型能在入口校验，返回模型可以清晰声明，接口文档也能自动生成，前端和外部 Connector 集成更方便。

Flask 足够轻量，但需要手动拼接更多校验、序列化和文档能力；在模型数量较多时，路由很容易退化成从 request.json 取任意字段。Django 自带完整 ORM、后台和模板体系，但本项目的主界面是独立 React，后端更需要轻量 API 和可替换 Repository，而不是传统服务端渲染和大而全的 Web 框架。FastAPI 正好处于两者之间。

FastAPI 并不意味着所有业务都应写成 `async def`。数据库、浏览器和部分第三方库可能有同步调用，项目将耗时采集放在服务和后台执行边界，路由只负责快速响应。异步框架的价值在于不让等待 HTTP、任务查询和控制接口相互阻塞，而不是强行把所有函数改成协程。

在面试中可以说：

> 选 FastAPI 不是因为它“新”，而是它把类型提示、Pydantic 校验和 OpenAPI 集成在一起。这个项目的 API 包含很多嵌套任务状态和控制接口，类型化契约可以显著减少前后端字段不一致，同时异步 Web 层适合处理轮询和外部 I/O。

### 23.3 为什么选 Pydantic，而不是普通 dict 或 dataclass

地图、模型、公开网页和 ERP 返回的数据都不可靠：字段可能缺失、类型可能变化、日期可能是字符串、电话号码可能不是号码。若在业务代码中一直传递 `dict[str, Any]`，每个函数都要重复做 `get`、类型判断、默认值处理，最后很难知道一个 Lead 到底应该有哪些字段。

Pydantic 模型将数据契约显式化。`MapPoiCandidate` 规定 POI 的结构，`LeadRecord` 规定业务线索结构，`EvidenceValue` 规定字段证据结构，`CollectionTask` 和 `CollectionWorkUnit` 规定状态与统计结构。模型创建时自动处理类型转换和默认值，序列化时可稳定输出 JSON。对于 API 层，错误输入可以快速返回 422；对于存储层，模型转储与恢复也更统一。

普通 dataclass 也能表达结构，但不提供同等程度的运行时校验和 JSON 序列化能力；纯 TypedDict 只在静态检查期有帮助，外部输入仍需手动验证。因此本项目使用 Pydantic 表达边界数据和领域对象，用简单 Python 函数表达纯规则。这样既有类型约束，也不会把所有业务逻辑塞进模型验证器。

### 23.4 为什么选 SQLAlchemy 加 SQLite

项目需要持久化的不是一张联系人表，而是一套任务运行历史：自然语言请求、解析意图、工作单元、候选企业、Lead、字段证据、checkpoint、批量任务、交付台账和结果消费记录之间存在关联。关系数据库适合表达这类状态与查询，而 SQLAlchemy 为领域对象和数据库表提供了隔离层。

SQLite 的选择基于部署目标。项目当前面向本地/内网使用，用户需要在能登录地图和模型的机器上启动服务；SQLite 是单文件数据库，不需要额外安装或维护服务器，备份和演示都简单。它足以支撑单应用进程、有限并发、任务与台账持久化的场景。

没有一开始选择 PostgreSQL，不是因为 PostgreSQL 不好，而是它会引入数据库服务、账号、网络、备份和运维成本。对于首先要证明“业务链路能跑通”的内部工具，SQLite 使交付路径更短。项目又通过 Repository 将业务服务与具体数据库隔离，未来迁移 PostgreSQL 时，主要替换连接配置、迁移脚本和少量并发控制，而不需要重写 Collection Service。

SQLAlchemy 的作用也不只是“少写 SQL”。它把表模型、事务、查询和 session 生命周期规范化。Repository 负责一次保存任务及其子对象，服务层避免直接依赖 ORM 行；单元测试可以创建临时数据库验证保存恢复；未来需要加索引、唯一约束和并发锁时，也有明确落点。

### 23.5 为什么依赖 Alembic

即使当前默认用 SQLite，数据结构仍会演进：最初可能只有任务和结果，后来增加工作单元、证据状态、交付指纹、账号范围和结果消费记录。如果只靠“删除数据库重新建表”，历史任务和台账会丢失；如果让每个开发者手工修改 schema，环境会很快不一致。

Alembic 提供版本化迁移能力，能把“数据库如何从版本 A 变为版本 B”写成可回放脚本。它在当前代码中作为依赖保留，为后续表结构演进建立基础。面试中可以说明：项目当前的规模不一定需要复杂数据库集群，但只要任务状态和交付台账需要保留，就必须为 schema 演进预留正规路径。

### 23.6 为什么选 Playwright 加 CDP，而不是 Selenium 或纯爬虫

地图网站的核心价值不仅在 HTML 内容，还在真实浏览器会话：登录状态、动态渲染、地图详情面板、异步加载、弹窗、跳转和安全验证。纯 requests 抓 HTML 往往拿不到完整信息，也无法处理用户已登录浏览器中的状态。项目因此选择浏览器自动化。

Playwright 相比 Selenium 提供更现代的页面等待、Locator、上下文隔离和异步支持，API 对动态页面更友好。CDP 连接方式让项目可以控制已有或专用的 Chrome，而不是每次运行都启动无法保留登录状态的无头浏览器。用户可以在独立 profile 中手动登录和完成安全验证，系统随后在相同会话中继续采集。

项目没有把浏览器自动化包装成“无条件无人值守爬取”。反而明确区分需要人工登录与需要安全验证的状态，并在任务中暂停。这既符合实际技术限制，也避免将不确定页面状态伪装成普通网络错误。Selenium 也能做浏览器驱动，但在新项目中 Playwright 的等待和上下文管理通常更一致；纯爬虫则无法满足当前网页登录和可见详情抽取需求。

### 23.7 为什么前端选 React、TypeScript 与 Vite

前端需要处理的是一个长期运行的操作工作台，而不是只展示一页静态结果。用户会创建任务、修改模型选项、启动、暂停、恢复、取消、过滤结果、单条交付、批量交付，并且任务状态会持续变化。React 的组件模型适合将这些界面拆为任务表单、任务状态、工作单元、统计、结果表和交付区域；状态变化后 UI 可以由数据重新渲染。

TypeScript 在这个项目中不是可有可无的装饰。后端状态很多，`completed_with_errors`、`needs_attention`、`display_only`、`duplicate` 等拼写错误或漏处理会直接导致 UI 误导用户。联合类型和接口让状态、结果、证据和 API 响应具有明确形状，配合 `tsc --noEmit` 可以在构建前发现契约问题。

Vite 的选择是为了快速开发和简单构建。它提供现代开发服务器、快速热更新和 TypeScript 构建整合，配置量比传统 Webpack 少，适合内部工具。没有一开始选 Next.js，因为当前应用不需要服务端渲染、SEO、复杂路由或全栈 React 能力；前后端已有独立 FastAPI API，Vite SPA 的边界更简单。

### 23.8 为什么使用 HTTPX、OpenPyXL 和标准库 HTMLParser

HTTPX 提供同步和异步 HTTP 能力、超时配置和清晰异常模型，适合 ERP、地图 API 和公开网页访问。相比直接使用低层 urllib，HTTPX 的调用体验和测试替换更好；相比引入过多 SDK，HTTP API 的请求和错误映射更透明。

OpenPyXL 用于 XLSX，是 Python 生态中成熟的 Excel 读取方案。业务人员经常从 Excel 导入公司列表，因此支持 XLSX 比只支持 CSV 更贴近实际工作流。CSV 则用标准库处理，减少额外依赖，并保持 UTF-8 读取逻辑明确。

公开网页解析使用标准库 HTMLParser，而没有在当前阶段引入大型爬虫框架。该模块只需要从有限页面提取链接、标题和可见文本，不需要复杂 CSS 选择器、分布式抓取或网页渲染。轻量解析器依赖少、攻击面小、部署简单。若未来需要处理结构复杂的站点，可在 Provider 内替换为 BeautifulSoup、lxml 或浏览器渲染，业务服务不用改变。

### 23.9 为什么使用 Protocol 和 Fake Provider

Provider Protocol 是 Python 的结构化接口约定。例如地图能力需要 `search_company`，模型补全需要 `enrich_company`，ERP 需要 `build_payload`、`fingerprint` 和 `deliver`。服务依赖“能力”，而不是依赖某个具体类名。这种依赖倒置使 Amap Web、Amap API、Fake Map 可以互换，也使未来更换模型供应商时无需改动任务编排。

Fake Provider 不只是测试用的 mock。它是对业务接口是否设计合理的检验：如果用一个内存 Fake 就能完整模拟成功、无结果、超时、登录等待、验证失败和 ERP 失败，说明服务层没有偷偷依赖页面对象或 SDK 细节。反之，如果测试必须启动 Chrome 才能跑核心业务，说明边界设计不够干净。

### 23.10 技术债与“没有选择”的技术

项目没有使用消息队列、Redis、Celery、Kubernetes、微服务、GraphQL 或大型状态管理库。这不是遗漏，而是与当前范围匹配的取舍。内部采集工具在早期最需要的是稳定完成一条闭环，而不是搭建多租户平台。过早引入这些组件会增加部署、监控、认证、网络和故障恢复成本，反而拖慢业务验证。

不过不选不等于永远不用。任务量增加时，进程内 worker 可迁移到 Celery/RQ；多用户并发时 SQLite 可迁移 PostgreSQL；多个浏览器 worker 可由队列调度；前端跨页面协作状态复杂时可再引入 Zustand 或 Redux Toolkit；外部系统接口规模变大时可增加 API Gateway 和鉴权服务。当前的 Provider、Repository、Task 和 Connector 边界为这些升级留出了空间。

## 24. 典型业务请求的逐层调用示例

下面用一个具体需求说明“从点击页面到写入 ERP”每层代码的职责。假设用户输入：

> 帮我在深圳找住宅装修和全屋定制公司，需要有效手机，目标 30 条，持续采集，手机经过验证后自动投递。

### 24.1 前端发起创建

用户在 `CollectionWorkbench.tsx` 输入文本，勾选连续模式和验证后自动交付。组件将表单状态组装成 `CreateCollectionTaskInput`，调用 `api.ts` 的 `createCollectionTask`。统一 request 函数添加 JSON Content-Type、处理响应状态，并将非 2xx 的后端 detail 转为前端可展示错误。

这里前端不把“深圳”“30”“手机”分别拆成十几个隐藏字段，因为用户的输入天然是自然语言；但它仍会传递显式的执行选项，例如 continuous_mode、auto_deliver 和 verified_auto_deliver。这样自然语言负责业务意图，明确的开关负责用户授权，避免模型误把一句话解释为自动投递许可。

### 24.2 API 生成计划

Collection 路由接收请求后，先验证模型选择和交付模式是否合理，再调用 Service 的 `create_from_text`。Service 调用 `parse_collection_intent`，从句子中识别深圳、住宅类关键词、手机号和目标数量。住宅语义触发关键词矩阵扩展，目标数量变为 `target_valid_contacts=30`。

接着 Planner 以“深圳乘每个关键词”创建工作单元，并使用任务种子、城市、关键词、Provider 生成稳定 ID。任务状态为 planned，摘要尚为零，所有单元为 planned；Repository 将它保存。路由返回任务、计划和单元列表，前端展示给用户。到这里没有访问地图，没有消耗模型，也没有产生 ERP 副作用。

### 24.3 启动后的第一个工作单元

用户点击开始，前端调用 start 接口。Service 将任务状态切到 running，checkpoint 当前阶段改为执行采集，后台执行器选取第一个 planned 单元，例如“深圳 + 全屋定制公司”。它首先尝试公开网页公司名发现，得到若干 `CompanyNameCandidate`；若公开结果不足，再使用地图关键词搜索补充公司名。

每个名称都会经过公司身份判断：是否已在任务中出现、是否在更早单元已经精确查询、是否存在明显竞争或无关词。如果已处理，则保留必要来源但跳过重复搜索；如果是楼盘、家具卖场或其他硬无关项，则记录拒绝，不浪费地图详情请求。

### 24.4 精确地图查询与候选写入

对于一个新公司名，Service 调用地图 Provider 的 `search_company(company_name, city)`。若配置 Web Provider，调用会经 Browser Actor 串行提交到 Chrome；Adapter 读取结果卡片并打开详情，验证页面仍是该公司。如果配置 API Provider，则调用地图 API 并映射 POI。两种实现返回相同的 MapPoiCandidate。

Service 再检查候选名称是否与公司名精确或可接受地匹配，候选城市是否为深圳，避免同名企业在东莞或广州被错误收入。通过后候选保存到任务，并附带地图 URL、POI ID、地址、电话、原始文本和来源 metadata。这个保存发生在模型补全前，因此即使模型随后失败，地图事实仍然存在。

### 24.5 相关性、补全与验证

若任务配置了模型，Service 将候选与目标关键词交给 Relevance Judge。模型返回相关、无关或复核；结果被 Parser 校验后写入 `relevance_decisions`。无关候选增加 rejected 统计，复核候选保留给页面展示，相关候选继续。

补全 Gateway 提取可能的联系人、邮箱、微信和简介。Merge 函数遵循地图优先，不允许模型将一条座机或猜测号码覆盖已有手机。之后 Public Evidence Provider 或地图证据验证器检查手机来源，生成字段级 EvidenceValue。只有手机合法、来自可信地图详情或达到独立验证条件时，才会成为 verified lead。

### 24.6 达标、投递和后续单元

Service 使用标准化手机号计算唯一有效线索数。重复手机号不重复计数，座机不计数。若尚未达到 30 条，则继续处理下一个公司和下一个关键词；若已经达到目标，后续单元标记为 skipped_limit 或不再启动，任务以 target_reached 结束。

对于满足 verified_auto_deliver 的 Lead，Service 调用 ERP Adapter。Adapter 生成 payload 和 fingerprint；台账未命中时发送 HTTP 请求，成功后记录 delivered，失败后记录 failed。若因恢复、刷新或重复点击再次处理相同 payload，台账直接返回 duplicate，不重复提交。前端轮询后可看到有效手机数、已交付数、失败数和来源链接。

## 25. 可以量化的工程指标与监控思路

当前工作台已经有任务摘要，但当项目进入持续运行阶段，还需要将关键质量和稳定性指标系统化。即使没有立即接入 Prometheus 或 Grafana，也应该先明确要测量什么，因为指标反过来会检验架构是否合理。

第一类是漏斗指标：每个工作单元的公司名发现数、地图精确匹配数、相关企业数、拥有联系方式数、已验证数、可投递数和 ERP 成功数。它能定位转化损失发生在哪里。例如公司名很多但精确匹配少，可能是命名或城市过滤过严；地图匹配多但手机少，可能是来源数据本身稀缺；验证后投递少，则要检查证据门禁或 ERP 配置。

第二类是 Provider 指标：地图搜索成功率、平均等待时间、超时次数、登录暂停次数、挑战暂停次数、模型解析成功率、公开证据命中率、ERP 延迟和失败码分布。Provider 是外部不确定性的主要来源，按 Provider 统计比只看“任务失败”更可操作。

第三类是任务可靠性指标：平均恢复次数、从创建到完成的时长、工作单元重试次数、completed_with_errors 比例、任务重启后恢复成功率、重复投递阻止次数。重复投递阻止次数尤其能验证 fingerprint 和台账是否真的在发挥作用。

第四类是数据质量指标：唯一手机号比例、座机误判率、跨城市误匹配拒绝率、模型复核比例、来源覆盖率、被人工确认无效的比例。数据质量不是一次开发后永久固定，需要根据抽检反馈调整关键词、精确匹配策略和证据规则。

## 26. 面试时的技术栈表达模板

当面试官问“项目用了什么技术栈”，不要只报一串名词。可以用“技术、用途、选择理由、结果”四段式回答。

> 后端我使用 Python 3.12 和 FastAPI。Python 适合这个项目的浏览器自动化、数据处理和外部服务编排；FastAPI 把类型提示、Pydantic 校验和接口文档整合在一起，适合任务控制和嵌套结果对象。领域数据用 Pydantic 建模，避免在多 Provider 链路中传递无约束 dict。

> 持久化使用 SQLAlchemy 加 SQLite。因为当前是本地或内网部署的采集工具，SQLite 免运维，能保存任务 checkpoint、工作单元、结果与交付台账；SQLAlchemy Repository 将业务与数据库隔离，后续可以平滑迁移 PostgreSQL。数据库迁移能力通过 Alembic 预留。

> 地图网页部分选择 Playwright 通过 CDP 控制专用 Chrome。原因是需要保留人工登录状态、处理动态页面和安全验证；我们没有把登录问题当成普通异常，而是映射为可恢复任务状态。地图 API 和网页采集统一为 Provider，业务层只处理 Candidate。

> 前端使用 React、TypeScript 和 Vite。React 适合任务工作台的动态状态，TypeScript 对复杂任务状态和证据字段提供保护，Vite 保持开发与构建轻量。测试后端用 Pytest 和 Fake Provider，前端用 Vitest、typecheck 和 build，重点验证长任务恢复、去重、证据门禁和幂等交付等业务不变量。

这段回答既包含技术栈，也体现了你理解每个技术为什么存在。面对不同职位可以调整重心：后端职位重点讲 Provider、状态机、数据库和测试；全栈职位再补 React 工作台和 API 契约；数据/AI 相关职位重点讲模型输出约束、证据与数据质量。
